Test run 过了才响的晨报

阅读约 7 分钟·核对日期 2026-10-20
事实来源

docs.x.ai/grok-bot/skills-routines-and-automations · docs.x.ai/grok-bot/settings-and-notifications · docs.x.ai/grok-bot/troubleshooting · docs.x.ai/grok-bot/mobile

例程的价值在于合上笔记本之后它还在跑。但没验证过就上线的定时任务，只会变成每天早上的噪音。官方给的做法很明确：先用 Test run 真跑一次，通过了再启用。这一篇把「每天早上八点一份晨报」拆成可复现的步骤。

适用

  • 你有固定的、早晚要看一眼的信息需求：昨天的进展、今天要决定的事、某几篇文档的变化。
  • 输入源稳定，格式不会天天变。
  • 你能接受它失败时不发——失败要留下痕迹，而不是拿旧数据凑一份看起来正常的晨报。
  • 你希望它是后台跑的：官方说明后台例程在你合上笔记本后依然运行。

不适合：源数据经常断、每次都要人工补的场景；或者你需要它在无人值守时替你发出去的动作——官方明确要求发送、购买、删除、发布、改生产系统一律审批，例程也不例外。

准备

Bot。 建一位专门管这件事的 Bot，描述写清它负责哪几件固定的事。导入 晨号 · 例程管家 模板即可，它的默认职责就是「每日晨报 08:00，Test run 过了才上线」。

技能先行。 官方顺序是：先把它做成一件能重复做对的事（技能），再让它按时间跑（例程）。技能要写清六件事：什么时候用、需要哪些输入与访问、工作步骤、怎么验证结果、交付什么、什么需要审批。写技能时把「失败时贴日志摘要、不要用旧数据顶替」写进失败处理那一条。

输入源。 例程的输入源就是它每次去取数据的地方：某个连接器、某个工作区文件、某个网页。连接器用 Connect apps 装好并授权，在例程说明里点名。

时区与权限。 在设置的 Bot 一节确认 Timezone，例程时间表按它算。审批边界保持收紧：Auto Review 里加一条 Ask first，范围写「发送任何外部消息前先问我」。

桌面端。 官方说明：手机端可以暂停或恢复例程，但编辑例程说明和跑 Test run 目前需要桌面端。这条流程请在桌面上做。

步骤

  1. 先跑一次一次性的任务。 用五要素下这一单，收到成果卡、你认可格式之后，再谈定时。

  2. 把做法存成技能。

存一条晨间简报技能
把我们刚才这套简报流程存成技能，叫「晨间简报」。
写清楚：来源系统、判断标准、输出格式、失败处理，以及「任何外发都要先问我」这条规则。
  1. 向要拥有这条例程的 Bot 下达创建指令。 官方确认六项：归属哪个 Bot、时间表与时区、输入来源、预期结果、审批边界、数据源缺失时怎么办。Bot 会创建例程并显示下一次运行时间。
官方风格的例程指令
每个工作日早上 8:00，对当前清单跑一遍「晨间简报」技能。
在本对话贴一份带链接的简报。不要替我发任何消息。
若源数据不可用，报告失败，不要用旧数据凑数。
  1. 用 Test run 验一次。 官方提醒：Test run 会真的做事——它会浏览网页、改文件、调用已连接的工具。用安全输入，把写操作留在审批后面。跑完逐条看五件事：
  • 选到的是当前数据，还是过期缓存；
  • 输出格式是否符合约定；
  • 每一步是否有来源或可追溯记录；
  • 是否停在了你要的审批点；
  • 失败状态是否写得清楚。

  1. 只有通过才启用。 例程在启用状态下才会自己跑。顺序别反：Test run → 看结果 → 启用。

  1. 定期回看。 打开 Bot 的 View conversation details，进 Routines，可以启用或暂停、跑一次测试、改时间表或说明、查看最近的成功与失败记录、删除。
失败时的例程指令
每天早上 8:00 跑「晨间简报」技能。
如果源不可用或抓取失败：不要发简报，只贴一条失败摘要，
写明是哪个源、什么时间失败、错误信息是什么。

失败摘要这一条很值得写进去：它把「失败」变成一个可交付的结果，而不是沉默。

你要检查什么

第一次启用后，头几天重点看这几项：

  • 简报里的每条结论都带来源链接，点开对得上。
  • 数字与条目能对上来源系统，没有凭空多出来的总结。
  • 事实与推测分开标注；没核实的说法有没有被单独标出。
  • 失败那天的记录是「失败摘要」而不是一份内容陈旧的晨报。
  • 它没有替你把简报发到任何外部渠道。
  • Needs attention 状态有没有积压的审批或提问——设置里这个提示专门标出等你回应的问题、审批或交接。

如果某天例程没跑，官方排查清单是：例程是否已启用、时间表与时区是否正确、归属的 Bot 是否还在、所需插件是否仍然保持授权、云电脑能否连到源系统、用量或账号访问是否被暂停。事件触发的例程还要确认源频道、仓库和匹配规则是否还有效。

审批边界

审批

例程推给你的内容不外发；但凡是替你发出去的动作，仍要过审批卡——哪怕触发它的是定时任务。

无人值守时产生的审批大约十分钟后过期，卡片显示 Expired，动作不会执行。过期卡片有时会提供 Always allow this in the future，那只是把规则写进 Allow automatically，不会补跑那次动作。

官方给的设计建议：先自动化「准备」环节——起草、对账、推荐；把发送、购买、删除、发布、改生产系统留在审批后面。同时给例程写一份「无数据 / 旧数据策略」，让重试尽量幂等，并告诉它部分完成时该在哪里报告。

另有一条容易被忽略的机制：长时间不在时，Grok Bot 可能询问是否继续运行例程，没有回应就可能暂停它。你回来后记得检查被暂停的例程。

出处说明

本文的流程全部依据官方 Skills and routines、Settings and notifications、Troubleshooting、Mobile 四页写成，没有引入社区转述。定时情报的一种用法——每天分三个时间整理 X 时间线、另有一个只盯官方账号的发布雷达——属于个人实践，本文只在「写失败策略」处借用了它的思路，未把那些具体时间点当作官方建议；模板页 晨号 · 例程管家 是本站整理的导入模板。
